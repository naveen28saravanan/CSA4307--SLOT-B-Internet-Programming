Form analysis

1. Issues in the form configuration

Original

<form action="/submit" method="GET">
  <input type="text" name="username">
  <input type="password" name="password">
  <button type="button">Login</button>
</form>

Problems

  1. type="button" does not submit the form. This is the main bug.
  2. method="GET" puts the password in the URL.
  3. No <label> elements, so screen readers cannot name the fields.
  4. No required, autocomplete or validation.
  5. No HTTPS, CSRF protection or rate limiting.

2. Why the HTTP request is not triggered

A <button type="button"> has no default action. The browser only builds and sends a request when a submit event fires, and that happens for type="submit" buttons (or an <input type="submit">). With type="button" clicking does nothing unless JavaScript adds a handler, so no request leaves the browser.

3. Role of GET in this scenario

GET sends form data as a query string in the URL. If the button did submit, the browser would request:

GET /submit?username=student&password=Simats%402026 HTTP/1.1

The password would then appear in the address bar, browser history, server logs, proxy logs and the Referer header. GET is meant for safe, repeatable reads such as search, never for credentials. See the GET vs POST demo.

4. Corrected implementation

Fixed

<form action="/submit" method="POST">
  <label for="username">Username</label>
  <input type="text" id="username" name="username"
         autocomplete="username" required>

  <label for="password">Password</label>
  <input type="password" id="password" name="password"
         autocomplete="current-password" required minlength="8">

  <button type="submit">Log in</button>
</form>

The Login page uses this exact structure.

5. Improvements for secure data transmission

MeasureWhy it matters
Serve over HTTPS (TLS)Encrypts the request so passwords cannot be read in transit.
Use POSTKeeps credentials out of URLs, history and logs.
Hash passwords on the serverUse bcrypt or Argon2 with a salt, never plain text.
CSRF tokenStops other sites from submitting the form on a user's behalf.
Secure cookiesSet HttpOnly, Secure and SameSite on the session cookie.
Rate limiting and lockoutSlows brute-force guessing.
Server-side validationClient checks can be bypassed.
HSTS and a CSP headerForces HTTPS and limits script injection.
